# Сборка с профилем (PGO) для Android, 7 ноября 2026

На Xiaomi 15T (Dimensity 8400, Cortex-A720) сборка лифтнутого кода по профилю выполнения
даёт больше, чем все остальные правки этой ночи вместе: **40.7 против 30.9 кадров в секунду**
при одинаковой нагрузке (51 тысяча вызовов Direct3D 9 на кадр, медиана двухсекундных окон
двух прогонов каждой сборки, `scripts/bench_compare.py`). Ожидание рендер-потоком машинного
лока падает с 7.7 до 4.9 мс на кадр.

Причина в структуре сгенерированного кода: 27 тысяч лифтнутых функций, каждая с ветвлениями
на каждое условие x86 и вызовами через `nfs_icall_resolve`. Компилятор без профиля не знает,
какая ветвь горячая, и раскладывает их одинаково. На x86-коде 2004 года, где горячий цикл
применения состояний D3DX (`sub_00669296`) выполняется 109 миллионов раз за прогон, это
стоит дорого.

Профиль **не хранится в репозитории**: он производный от SPEED2.EXE (имена лифтнутых функций
и счётчики их блоков), как и сам сгенерированный C. Его собирают заново по шагам ниже.

## Сбор профиля

Инструментированная сборка (`-fprofile-generate -fprofile-update=atomic`; атомарные счётчики
нужны, потому что рядом с гостевым кодом работают хостовые потоки: колбэк AAudio, сторож
зависаний, таймерный воркер):

```
cd android
./gradlew assembleDebug -PnfsCpu=cortex-a720 -PnfsFast -PnfsPgo=generate
```

Сборка занимает около 17 минут, APK вырастает до 194 МБ, кадровая частота падает примерно
до 30 — это нормально и на результат не влияет.

Прогон пишет счётчики по сигналу: рантайм раз в секунду смотрит файл
`<внешние файлы приложения>/pgo/dump` и, увидев его, выгружает `default_<хеш>.profraw`
из отдельного потока (выгрузка занимает секунду-две и не должна блокировать кадр).
`%m` в имени означает, что все прогоны сливаются в один файл.

```
python -I scripts/android_bench.py --label pgo-gen \
  --apk release/<инструментированная>.apk --menu "$(cat work/bench/menu.txt)" \
  --settle 4 --race-seconds 40 --pgo-dump work/pgo
```

Прогонять стоит и гонку, и меню с гаражом (`--no-gas`), иначе фронтенд останется без профиля.
Использованный набор: две гонки по 40 секунд плюс один проход по меню.

## Сборка по профилю

```
C:/Android/Sdk/ndk/<версия>/toolchains/llvm/prebuilt/windows-x86_64/bin/llvm-profdata.exe \
  merge -output=work/pgo/nfsu2.profdata work/pgo/*.profraw

cd android
./gradlew assembleDebug -PnfsCpu=cortex-a720 -PnfsFast \
  -PnfsPgo=use -PnfsPgoProfile=C:/dev/nfsu2-recompiled/work/pgo/nfsu2.profdata
```

APK вырастает со 141 до 161 МБ: по профилю компилятор агрессивнее встраивает горячие вызовы.

## Что обязательно должно совпадать

Профиль ключуется по имени функции и хешу графа потока управления **до** ThinLTO. Если
хеш не сошёлся, профиль для этой функции молча отбрасывается, и сборка выглядит удачной,
не будучи оптимизированной. Поэтому у `generate` и `use` обязаны совпадать:

- `NFS_GUEST_FAST` (меняет `RECOMP_BACKEDGE` в `arm64_guest.h`, то есть граф каждого цикла);
- `NFS_GUEST_OPT` и прочие флаги компиляции лифтнутого кода;
- вывод лифтера (`src/recomp/gen/`), то есть сборка SPEED2.EXE и `config/`.

Смена `-mcpu` граф не меняет, но менять её без пересбора профиля всё равно не стоит.
Переносимая (portable) сборка собирается без `NFS_GUEST_FAST`, поэтому ей нужен
**отдельный** профиль, собранный переносимой инструментированной сборкой.

Проверить, что профиль действительно содержит игровой код:

```
llvm-profdata.exe show --all-functions work/pgo/nfsu2.profdata | grep -c "^  sub_"
```

Должно получиться около 27 тысяч функций.
